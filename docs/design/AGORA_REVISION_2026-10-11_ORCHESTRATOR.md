## (2) 새 모델 — 방별 상태와 저장 위치

### 2.1 영속 설정(세션 메타, `permissionMode`와 같은 자리)

```
meta.orchestrator = { enabled: boolean, leadId: string | null }   // 기본 { enabled: false, leadId: null }
meta.keepCalling  = boolean                                        // 기본 false
```

`roomMeta(meta)`(chat-ipc.js:984)가 읽어 `room.setMeta()`에 실어 준다(지금 `permissionMode`·`workspace`와 같은 줄). IPC 두 개를 `chat:permission:set`과 같은 모양으로 더한다:

- `chat:orchestrator:set { sessionId, enabled, leadId }` — `leadId`는 `enabled`일 때 그 세션에서 쓸 수 있는(available && enabled!==false) 에이전트여야 한다. `store.updateMeta` 뒤 `room.setMeta(roomMeta(...))`를 부르고, **지금 활성 오케스트레이션이 있으면 끝낸다**(끄거나 지휘 AI를 바꾸는 것은 "모드 꺼짐"과 같은 정리 사유다 — §8).
- `chat:keep-calling:set { sessionId, enabled }` — 그대로 저장. 켜짐·꺼짐 모두 당장 돌고 있는 멘션 연쇄를 건드리지 않는다(다음 호출부터 적용).

둘 다 세션을 다시 열거나 창을 다시 붙여도 복원된다(영속). 화면: 입력창 위 응답 방식 줄(이어 발언/독립 발언) 옆에 "AI끼리 계속 부르기" 체크(결정 4), 방 머리줄(`room-bar`)에 [오케스트레이터] 칩 + 지휘 AI 선택(결정 1). 체크는 `orchestrator.enabled`와 무관하게 항상 보통 밝기로, 항상 클릭 가능하게 둔다(흐리게 그리지 않는다 — 2차 적대적 검토로 바뀐 기본값, §0·§10).

### 2.2 실행 중 상태(휘발성, `generation`·`activeUnits`와 같은 자리 — 재시작하면 사라진다)

```
this.orchestration = null | {
  id,                 // `o${sessionId}-${seq}`, orchestrationSeq로 발급
  leadId,
  round,              // 지휘 AI 턴이 지금까지 몇 번 돌았나(1부터)
  executions,         // 지휘 AI·작업자 턴을 합쳐 지금까지 claim된 수
  heldMessages: [],   // 이 사이 사용자가 지휘 AI에게 보낸, 아직 전하지 않은 메시지 텍스트
  ceilingNoticed: false,
}
```

하나의 방은 **한 번에 오케스트레이션을 하나만** 가진다(동시에 둘이 돌지 않는다 — 켜짐 상태에서 지휘 AI에게 가는 메시지는 §4에서 "이미 진행 중이면 held"로 빠지므로 둘째 오케스트레이션이 시작할 길이 없다).

왜 영속이 아닌가: v4·v5 어느 결정도 재시작 뒤 오케스트레이션을 이어가라고 하지 않았고(세션 메타는 설정이지 실행 상태가 아니다), 이어가려면 지휘 AI의 중간 판단·작업자 진행률을 복원해야 해 비용이 크다. 대신 **조용히 사라지지 않게** `shutdown()`이 `this.orchestration`이 있으면 `stopAllSilently` 전에 한 줄을 남긴다("오케스트레이터 ⟦지휘 AI⟧ 호출이 n라운드/실행 n회에서 앱 종료로 멈췄습니다. 다시 시작하려면 지휘 AI에게 메시지를 보내 주세요.") — 이 줄은 대화에 저장되므로 다시 열면 보인다.

### 2.3 시작 — 큐잉이 아니라 claim 시점에 만든다

지휘 AI에게 가는 메시지(§4의 "맡기기 시작" 행)는 **보통 턴과 같은 줄 규칙**을 그대로 탄다(바로 답하기의 빠른/일반 줄 판정이 손대지 않는다 — "오케스트레이션 시작"은 대상·멘션 모양만 다를 뿐 턴 하나이므로, `@지휘AI 해줘`는 지휘 AI가 비어 있으면 빠른 줄, 그 밖엔 지금 규칙대로다). 턴의 `context`에 `{ orchestrationStart: { leadId } }`만 얹어 둔다.

실제 `this.orchestration` 객체는 그 턴이 **claim될 때**(`claimUnit`) 만든다: 그 시점에 `this.meta.orchestrator.enabled`와 `leadId`가 아직 그 설정과 일치하고(큐에서 기다리는 동안 모드가 꺼졌거나 지휘 AI가 바뀌었으면 무시하고 그냥 보통 턴으로 돈다 — 안전한 기본값) `!this.orchestration`이면 새 id를 발급해 `round:1, executions:0`으로 만들고, 그 턴의 `context`에 `{ orchestration: { id, role: "lead", round: 1 } }`을 심어 `runResponseTurn`이 읽게 한다. 라운드 1의 `executions`는 이 턴이 실제로 claim된 순간 1이 된다.

왜 claim 시점인가: 큐에서 기다리는 동안(바로 답하기의 "대기") 상태가 바뀔 수 있는데, 스케줄 시점에 만들면 그 사이에 모드가 꺼져도 오케스트레이션이 "시작된 적"으로 남아 정리할 것이 생긴다. claim 시점에 만들면 시작하지 않은 오케스트레이션은 아예 존재하지 않는다(정리할 것이 없다).

**줄(lane): 지휘 AI의 첫 턴만 사용자 메시지 규칙을 받고, 그 뒤 모든 오케스트레이션 턴은 항상 빠른 줄이다.** 지휘 AI의 첫 턴(이 메시지)은 §(3)의 "맡기기 시작" 경로를 타는 **사용자** 메시지이므로 `isFastEligible`의 보통 적격 판정을 그대로 받는다(지휘 AI가 비어 있으면 빠른 줄, 아니면 지금 규칙대로). 그 뒤로 지휘 AI가 스스로 만드는 작업자 묶음과, 작업자 묶음이 끝난 뒤의 지휘 AI 회신 턴은 **사용자 메시지가 아니라 방이 직접 스케줄하는 턴**이다 — `scheduleTurn`을 부를 때 `placement.lane = "fast"`를 **항상** 명시한다(§2.2의 적격 조건은 사용자 메시지만 거치는 문이고, 시스템이 직접 만드는 턴은 그 문을 거치지 않고 바로 빠른 줄에 선다). 이렇게 두는 이유는 둘이다: (a) "직접 @other는 바로 답하고, 오케스트레이션은 곁가지와 나란히 간다"는 결정을 그대로 구현하려면 오케스트레이션 턴이 다른 **일반** 줄 항목(다른 대화의 멘션 호출 연쇄 등) 뒤에서 기다리면 안 된다 — 일반 줄은 `activeUnits`가 빌 때만 시작하므로(§2.4(c) 뒤로는 "오케스트레이션이 아닌 활성 단위가 없을 때"), 메인 줄로 두면 곁가지 대화의 멘션 호출이 앞서 있을 때 작업자 묶음이 밀릴 수 있다. (b) `claimUnit`(chat-room.js:946)의 "시작 시점 기록·`replyTarget` 다시 세기"는 `item.lane === "fast" || item.context.independent`일 때만 켜진다 — 빠른 줄로 두면 §(7)에서 약속한 "claim 시점까지 끝난 결과를 모두 본다"가 **코드를 더 손대지 않고** 그대로 성립한다(작업자는 `context.independent`도 true라 이중으로 보장된다). 묶음이 claim되는 순간(지휘 AI 턴이 끝난 그 패스에서 곧바로) `history.at(-1)`은 지휘 AI 자신의 답이고 그 id가 작업자의 `turnRootId`와 같으므로 `replyTarget`은 항상 비워진다(= "마지막 메시지에 이어 답하세요"라는 기본 문구가 그대로 맞다 — 지휘 AI의 지시가 실제로 대화의 마지막이기 때문이다). 지휘 AI의 회신 턴도 같은 이유로 claim 시점 기록을 쓰지만, 그 턴이 실제로 무엇에 "답하는지"는 `replyTarget`이 아니라 `extraLines`의 결과 블록이 정하므로(§(7)) `replyTarget`이 비든 차든 무해하다.

### 2.4 토론·메인 줄과의 교차점(적대적 검토로 고친 것)

적대적 검토 2명이 독립적으로 같은 자리(스케줄러의 두 상태 `discussionRequested`·`activeUnits`)에서 서로 다른 구멍을 찾았다. 둘 다 "오케스트레이션 턴은 항상 빠른 줄"이라는 위 §2.3의 전제가 다른 메커니즘과 맞물릴 때 생긴다.

**(a) 토론 시작 버튼이 오케스트레이션 중에도 눌린다.** `startDiscussion`은 지금 `this.orchestration`을 전혀 보지 않는다 — `discussionRequested = true`를 동기로 세운 뒤 `waitForIdle()`로 조용히 기다린다. 오케스트레이션 중에 눌리면 즉시 거절되지 않고 그냥 멈춰 버린 것처럼 보이고(틀린 O18), 더 나쁘게는 `scheduleTurn`의 줄 계산(`lane: ... && !this.discussionRequested ? "fast" : "main"`)이 `discussionRequested`가 true인 동안 **새로 스케줄되는 모든 턴**을 메인 줄로 떨어뜨린다 — 오케스트레이션의 작업자 묶음·회신 턴도 예외가 아니다. 위 "오케스트레이션 턴은 항상 빠른 줄"이 통째로 깨진다.

**고침**: `startDiscussion`은 함수 맨 앞, `discussionRequested`를 건드리기 **전에** `this.orchestration`을 본다 — 있으면 `{ ok:false, error:"오케스트레이션이 끝난 뒤에 토론을 시작할 수 있습니다." }`를 바로 돌려주고 끝낸다(지금 쓰는 "토론에는 두 명 이상 필요"류 조기 거절과 같은 자리·같은 모양). 이렇게 두면 **`discussionRequested`가 true인 어느 순간에도 `this.orchestration === null`**이 성립하므로(§13 불변식 1), 오케스트레이션이 살아 있는 동안 생기는 작업자·회신 턴의 `scheduleTurn` 호출은 `discussionRequested`를 절대 true로 볼 일이 없다 — `scheduleTurn`의 줄 계산 자체는 고치지 않는다(루트 원인 한 곳만 막는다).

방어적으로 한 겹 더: §2.3의 claim 시점 조건("`this.meta.orchestrator.enabled`와 `leadId`가 일치하고 `!this.orchestration`이면 생성")에 `&& !this.discussionRequested && !this.discussionActive`를 더한다. 위 고침만으로 충분하지만(토론 요청 중엔 애초에 `this.orchestration`이 설 수 없다), 지휘 AI에게 가는 메시지가 **스케줄된 뒤**(아직 claim 전, 그 담당자가 바빠 대기 중일 때) 사용자가 토론 시작을 누르는 좁은 창은 이 조건이 없으면 "오케스트레이션을 막 시작하려는 순간에 토론도 요청된" 상태가 될 수 있다 — 이 조건이 있으면 그 메시지는 **보통 턴으로** 돈다(오케스트레이션을 만들지 않는다). 이때 사용자가 "맡겼다"고 생각한 일이 조용히 보통 대화가 되므로, claim 순간에 한 줄: `"오케스트레이션이 토론 시작과 겹쳐 이번 요청은 보통 대화로 처리합니다. 토론이 끝난 뒤 다시 말씀해 주세요."`를 낸다(§(3) 표의 "토론 중" 줄, §(15) 받아들이는 위험).

**(b) `this.orchestration`이 null로 돌아가도 기다리던 토론이 못 깰 수 있다.** `isIdle()`이 `this.orchestration === null`을 보게 바꾸면(§13 불변식 1), `resolveIdleWaiters()`는 **그 값이 null이 된 뒤에** 불려야만 `startDiscussion`의 `waitForIdle()` 루프가 풀린다 — `resolveIdleWaiters()` 자신이 `isIdle()`이 거짓이면 그냥 돌아가기 때문이다(아무도 안 깨운다). 오케스트레이션을 끝내는 모든 자리가 "① `this.orchestration = null` 먼저 → ② `resolveIdleWaiters()`" 순서를 지켜야 한다. **고침**: §(8)의 공용 헬퍼 `endOrchestration(notice)`가 이 순서를 한 곳에서 강제한다. `stopAllSilently`(중지·잠깐·삭제·종료가 공유)만은 이 헬퍼를 쓰지 않고 직접 `this.orchestration = null`을 두지만, 반드시 **기존의 `this.resolveIdleWaiters()` 호출(지금 코드 끝자락, 2049줄)보다 앞**에 둔다 — 새 줄 하나를 기존 호출 앞에 넣는 것뿐이라 자리를 명시해 둔다.

**(c) 메인 줄이 오케스트레이션이 도는 동안 굶는다.** `pumpPass`의 2단계(메인 줄 시작)는 `this.activeUnits.size === 0`일 때만 돈다. 오케스트레이션은 라운드마다(최대 50) 작업자 묶음→지휘 AI 회신 턴을 쉬지 않고 빠른 줄로 다시 올리므로(§2.3), 한 묶음이 끝나 `activeUnits`에서 빠지는 바로 그 동기 구간 안에서 다음 묶음이 빠른 줄로 다시 올라가 또 claim된다 — `activeUnits.size`가 실제로 0인 틈이 생기지 않는다. `@all`처럼 늘 그대로 가야 하는 메시지(§(0) 비판 검토, §(3))나 그 밖의 메인 줄 메시지가 오케스트레이션이 끝날 때까지(최대 50라운드) 전혀 시작되지 못한다 — "곁가지와 나란히 간다"는 결정과 어긋난다.

**고침**: 2단계의 게이트를 "활성 단위가 하나도 없다"에서 "오케스트레이션이 아닌 활성 단위가 하나도 없다"로 좁힌다 — `[...this.activeUnits].every(unit => unit.items[0].context.orchestration)`이면(활성 단위가 있어도 전부 오케스트레이션 턴이면) 메인 줄 머리를 그대로 시작한다. 오케스트레이션이 아닌 빠른 줄 작업(예: 직접 `@other` 대화)이 하나라도 돌고 있으면 지금처럼 메인 줄은 기다린다(기존 FIFO 보장은 오케스트레이션 턴에만 뚫는다). `stallBlockers`(줄 막힘 진단, 1129줄)의 메인 줄 분기도 같은 조건으로 고쳐야 "응답이 아직 차례를 기다리는 중"이라는 안내가 오케스트레이션 중에도 맞게 나온다(§(17)).

## (3) 메시지 라우팅표 — 모양 × 모드

ONE @ 규칙(결정 2)이 모든 줄의 바탕이다: **이름으로 부른 메시지는 모드와 무관하게 그 AI에게 간다.** 모드가 가르는 것은 **@ 없는 메시지의 수신자**뿐이다. `sendUserMessage`는 지금처럼 `parseMentions`로 모양을 가른 뒤, 아래 표의 목적지로 보낸다(걷어내기·자리·바로 답하기 규칙은 REPLY_NOW §2.5를 그대로 쓴다 — 오케스트레이션 턴은 §(6)에서 그 규칙의 예외를 명시한다).

| 메시지 모양 | 꺼짐(지금과 같음) | 켜짐, 오케스트레이션 **없음** | 켜짐, 오케스트레이션 **진행 중** |
|---|---|---|---|
| @ 없음 | 모두에게(보통 턴, 전원 방송) | **지휘 AI에게**(= 맡기기 시작, §2.3) | **보류**: 턴을 만들지 않는다. 메시지는 대화에 그대로 남고 `orchestration.heldMessages`에 쌓인다. 한 줄 안내(§8). |
| @지휘AI 만 | (지휘 AI에게, 보통 멘션) | 위와 **같다**(= 맡기기 시작) — "이름만 써도 되고 @로 불러도 같다" | 위와 **같다**(보류) |
| @다른AI 하나(지휘 AI 아님) | 그 AI에게 | 그 AI에게 **바로**(보통 멘션, 오케스트레이션과 무관) | **그 AI에게 바로**, 오케스트레이션은 그대로 간다(§8 "직접 @other"). 그 AI가 지금 작업자로 바쁘면 그 작업을 끝낸 뒤 이어서 답한다(바로 답하기의 담당자 게이트가 그대로 해 준다 — 새 코드 없음). |

## (4) 작업자 묶음(unit) — 재사용하는 것과 재사용하지 않는 것

**어디서 다음 단계를 건다 — 한 곳, 두 방향.** 지휘 AI의 턴도 작업자의 턴도 항상 "단위(unit)"로 claim된다(지휘 AI는 멤버가 1명뿐인 단위). 다음 단계(작업자 묶음 시작, 또는 지휘 AI 회신 턴 시작)는 **`runUnit`의 `finally`에서만** 건다 — `runResponseTurn` 안(§(6)의 멘션 호출 자리)에서는 절대 걸지 않는다. 이유는 타이밍이다: `runResponseTurn`이 아직 실행 중일 때는 그 턴의 항목이 `runningTurns`에 남아 있어(제거는 `runQueuedTurn`의 `finally`가 한다), 그 자리에서 작업자를 바로 스케줄하면 §(6)·§(7)의 `concurrentWork` 계산(`liveTurns()`에서 자기 단위를 뺀 나머지)이 **지휘 AI 자신을 "지금 돌고 있는 다른 참가자"로 작업자에게 알리는 거짓 줄**을 만든다(지휘 AI의 답은 이미 대화의 마지막 메시지인데 "그 답이 아직 없다"고 말하게 된다). `runUnit`의 `Promise.all`이 끝난 뒤(= 그 단위의 모든 `runQueuedTurn`이 이미 `runningTurns`에서 빠진 뒤)에 거는 것으로 이 창을 없앤다. 구체적으로: `claimUnit`이 단위의 첫 항목에 `context.orchestration`을 심어 두므로(지휘 AI 단위는 §2.3에서, 작업자 단위는 아래에서), `runUnit`의 `finally`는 `unit.items[0].context.orchestration?.role`을 보고 분기한다 — `"lead"`면 아래 설명대로 작업자 묶음을 짓고, `"worker"`면 §(7)의 결과 블록을 짓는다. 폴더 밖 변경 감시(`reportFolderContractBreaches`)는 `context.parallelGroupId`가 없는 한(= 모든 오케스트레이션 턴) 원래 안 불린다(§(4) 그룹 키 설명 참고) — 분기가 서로 간섭하지 않는다.

**분기 앞에 거는 공용 문**(적대적 검토로 추가). 역할을 보고 갈라지기 **전에** 먼저 `this.orchestration?.id === unit.items[0].context.orchestration.id`를 확인한다. 다르면(모드 끔·×취소·지휘 AI 못 씀·안전선으로 이미 끝났거나, 그사이 새 오케스트레이션이 또 섰거나) **역할이 `"lead"`든 `"worker"`든 아무것도 짓지 않고 조용히 돌아간다**(§(8)의 "폐기" 규칙을 작업자 결과뿐 아니라 지휘 AI 자신의 결과에도 똑같이 적용하는 것 — 모드 끔이 지휘 AI의 회신 턴이 **도는 중에** 와도, 그 턴이 끝났을 때 죽은 오케스트레이션으로 작업자를 새로 부르지 않는다). 이 문 하나로 `claimUnit`에 별도의 id 가드를 더하지 않아도 된다(이유는 §(15) — 큐에 남는 형제는 `endOrchestration`이 그 자리에서 치우므로 `claimUnit`이 죽은 항목을 볼 틈이 코드 구조상 없다).

**자리**: 이 분기(공용 문 + lead/worker 가지)는 `runUnit`의 기존 줄 `this.activeUnits.delete(unit);`과 `this.resolveIdleWaiters();`(990-994줄) **사이**에 넣는다 — 오케스트레이션이 그 자리에서 끝나면 `this.orchestration = null`이 유휴 대기자를 깨우는 `resolveIdleWaiters()`보다 먼저 서야 하고(§2.4(b)), 계속되면 다음 묶음이 이미 올라간 뒤에 유휴 검사를 해도 무해하다.

**작업자 묶음은 쪼개지지 않게 올린다**(적대적 검토로 추가). `scheduleWorkerUnit`은 작업자마다 `scheduleTurn`을 부르는 루프를 `sendUserMessage`가 쓰는 것과 똑같은 모양으로 감싼다 — `this.pumpSuspended += 1; try { ...루프... } finally { this.pumpSuspended -= 1; this.pumpTurnQueue(); }`. 감싸지 않으면 `scheduleTurn`은 `pumpSuspended === 0`일 때 자기 호출 안에서 바로 펌프를 돌리므로(650줄), 첫 작업자가 둘째 작업자가 큐에 오르기도 전에 혼자 claim돼 "한 묶음으로 같이 시작"(결정 3)이 깨진다.

지휘 AI 턴이 끝나면(위 지점, `unit.items[0].context.orchestration?.role === "lead"`일 때), 그 턴의 `outcome.text`를 `parseMentions(text, this.agents)`(그룹 별칭 **없이** 호출 — `isFastEligible`이 이미 쓰는 호출 방식과 같다)로 읽어 지휘 AI 자신을 뺀 멘션 id를 모은다. `parseMentions`가 이미 중복을 지운다(같은 AI 두 번 부르면 한 번만 — 결정). `outcome`이 `undefined`거나 `ok:false`면(지휘 AI 자신의 실패) §(8)의 "지휘 AI를 못 쓰게 됨"/실패 경로로 바로 넘어간다(작업자를 부를 지시 자체가 없다).

- id가 `enabledAgents()`에 없으면(비활성·미설치) **작업자로 시작하지 않고** 결과 블록에 "사용할 수 없음"으로 바로 적는다(턴을 claim하지 않으므로 `executions`에 안 들어간다).
- 나머지(실행 가능한) id가 **0개**면 이 라운드는 위임이 없다 — 지휘 AI의 이 답이 최종 답이다(§8 "지휘 AI가 @ 없이 답함"과 같은 취급. 멘션이 전부 그룹 별칭·자기 자신·비활성이었을 뿐이어도 같다).
- 1개 이상이면 **안전선 점검**(§(5))을 거친 뒤 한 묶음(unit)으로 같이 claim한다.

**재사용**: REPLY_NOW §2.1·§2.3의 "단위(unit)"·"담당자 게이트"·`claimUnit`/`runUnit`의 claim-후-실행 모양을 그대로 쓴다. 다만 독립 발언이 쓰는 `context.parallelGroupId`는 **쓰지 않는다** — 그 필드는 `buildAgentPrompt`의 무거운 "자기 폴더에만" 계약(`parallel`, chat-prompt.js:241)과 `runUnit`의 폴더 밖 변경 감시(`startedAt` 조건, chat-room.js:977)를 **둘 다** 켜는 스위치라서, 결정("독립 발언의 자기 폴더 계약과 폴더 밖 변경 감시는 작업자 묶음에 쓰지 않는다")대로라면 애초에 설정하면 안 된다. 대신 새 필드 `context.workerUnitId`(묶기용으로만 쓴다)를 두고, `unitOfQueued`(chat-room.js:875)가 그룹 키를 `item.context?.parallelGroupId || item.context?.workerUnitId`로 읽게 한 줄만 넓힌다. `claimUnit`의 "묶음 실제 크기 다시 세기"(`item.parallelTotal = members.length`)는 그룹 키 이름과 무관하게 그대로 동작하므로 손대지 않는다 — 다만 `parallelGroupId`가 없으므로 `buildAgentPrompt`의 무거운 계약은 자동으로 꺼진다(조건이 `context.parallelGroupId && ...`). 가벼운 동시 작업 계약(`concurrentWork`, 쓰기·읽기 방)은 이미 "같은 단위가 아닌 돌고 있는 턴"만 보므로 **그대로 재사용**한다 — 묶음 안의 형제 작업자는 서로를 보지 않고(설계대로), 묶음과 무관하게 **그때 마침 돌고 있는 다른 턴**(예: §(3)의 직접 @other 턴)은 정상적으로 보인다.

각 작업자는 `scheduleTurn(workerAgent, context, { lane: "fast" })`로 스케줄한다(§2.3에서 정한 "오케스트레이션 턴은 항상 빠른 줄"). 각 작업자 항목의 `context`에는 `orchestration = { id, role: "worker", round }`, `context.turnRootId = <지휘 AI 답의 메시지 id>`, `context.independent = true`(REPLY_NOW §2.6의 "독립 발언은 형제 답을 서로 안 본다" 필터를 그대로 빌려 쓴다 — 작업자들은 서로의 답을 보지 않는다), `context.attachments`(지휘 AI 답이 가리키는 사용자 메시지의 첨부를 그대로 물려준다), `context.extraLines`는 비워 둔다(작업자는 결과 블록을 받지 않는다 — 지휘 AI만 받는다, §(7)). **중복 방지 키는 보통 자유 대화 키(`turnRootId:agentId`)를 쓰지 않는다** — 대신 `orch:${id}:${round}:${agentId}`를 쓴다. 이유는 둘이다: (a) 지휘 AI의 답 메시지 id를 `turnRootId`로 재사용했으므로 보통 키와 같은 모양이면 그 뒤에 같은 메시지로 또 @멘션 호출이 와도 섞일 수 있고, (b) **더 중요하게**, `collectSupersedable`(chat-room.js:834)과 `isFastEligible`의 조건 6(나)(chat-room.js:420)가 "그 에이전트의, `turnRootId`가 있는 자유 대화 대기 턴"을 걷어내거나 막는 기준으로 쓰므로, 별도 키 공간을 쓰더라도 **이 둘은 반드시 작업자·지휘 AI 턴을 걸러야 한다**(아래).

> **중대한 교차점(바로 답하기와의 상호작용).** 사용자가 `@codex`를 직접 보냈을 때 codex가 마침 작업자 턴을 **큐에서 기다리는 중**(이론상 `pumpSuspended` 동안의 짧은 창)이면, 지금의 `collectSupersedable`은 그 대기 턴을 "갈아끼울 수 있는 자유 대화 턴"으로 보고 **지워버린다** — "새 사용자 메시지는 진행 중인 일을 버리지 않는다"는 불변식을 깬다. `isFastEligible`의 조건 6(나)도 같은 이유로 그 대기 턴을 "갈아끼울 수 없는 턴"으로 오인해 메시지를 일반 줄로 떨어뜨릴 수 있다(결과적으로 느려질 뿐 데이터를 잃지는 않지만, 결정("직접 @other는 바로 답한다")과 어긋난다). **고침**: `collectSupersedable`과 `isFastEligible` 조건 6(나) 모두 `item.context.orchestration`이 있는 항목을 **대상에서 뺀다**(걷어낼 수도 없고, 막는 걸로도 안 친다). 이미 **실행 중**인 지휘 AI·작업자 턴은 애초에 두 함수가 보는 큐(`turnQueue`/`deferredTurnQueue`)에 없으므로 영향이 없다 — 바로 답하기의 담당자 게이트(`agentIsRunning`)가 "그 담당자가 끝나면 이어서 시작"을 이미 보장한다(새 코드 없이 §(3)의 "바쁘면 끝내고 답한다"가 그대로 성립하는 이유).

## (5) 라운드·실행 횟수와 안전선

```
ORCHESTRATION_ROUND_CEILING = 50
ORCHESTRATION_EXECUTION_CEILING = 150
```

- `executions`는 claim되는 모든 오케스트레이션 턴(지휘 AI + 작업자)마다 1씩 오른다(`claimUnit`에서 `item.context.orchestration?.id === this.orchestration?.id`일 때).
- `round`는 지휘 AI 턴이 **새로** claim될 때마다 1씩 오른다(첫 턴이 1, 그 다음 회신 턴이 2, …).
- 안전선 점검은 **새로 무언가를 시작하기 직전**에만 한다(이미 시작한 턴을 중간에 끊지 않는다):
  - 작업자 묶음을 시작하기 전: `executions + 묶음 크기 > 150`이면 **묶음을 시작하지 않는다**. 지휘 AI의 그 답(이미 대화에 남아 사용자에게 보였다)에 적힌 @멘션은 그대로 실행되지 않고, 한 줄 안내("실행 횟수 안전선(150회)에 닿아 더 맡기지 않았습니다. 메시지를 보내면 이어 갑니다.")를 내고 오케스트레이션을 끝낸다(§8).
  - 지휘 AI의 다음 회신 턴을 시작하기 전(= 작업자 묶음이 끝난 뒤): `round + 1 > 50`이면 회신 턴을 시작하지 않고, 같은 모양의 안내("라운드 안전선(50)에 닿아 멈췄습니다. 메시지를 보내면 이어 갑니다.")를 내고 끝낸다. 이때 방금 끝난 작업자들의 결과는 화면(대화)에는 이미 메시지로 남아 있으므로 사라지지 않는다 — 다만 그 결과를 "본" 지휘 AI의 정리 답은 없다는 뜻이다.
- 2명 작업자 기준 50라운드 × (지휘 1 + 작업자 2) = 150이 "약 150회"의 근거다(계획 v4 §2-8과 일치). 작업자가 더 많으면 실행 상한이 라운드 상한보다 먼저 걸려 가지가 퍼지는 것을 막는다(계획 문구 "갈래가 퍼져도 합계로 막음"과 같은 안전판 역할).
- 화면에는 라운드·실행 횟수만 보인다(결정) — `room.state()`에 `orchestration: { active, round, executions, leadId } | null`을 더한다. "50라운드/150회" 숫자나 "왜 멈췄는지"의 자세한 사유는 화면 상시 표시가 아니라 **멈출 때의 안내 한 줄**로만 나온다(평소에는 카운터만).

## (6) `runResponseTurn`에 필요한 분기 — 바이트를 아끼는 지점

`context.orchestration = { id, role, round }`가 있을 때만 아래가 평소 경로와 달라진다. 없으면(보통 턴) **한 글자도 바뀌지 않는다**.

| 지점(현재 코드) | role 없음(지금) | role === "lead" | role === "worker" |
|---|---|---|---|
| `questionPurpose`(1285) | `isFreeChatContext && FILE_WORK_PERMISSIONS`면 `"chat"` | 그대로(지휘 AI는 보통 자유 대화 턴과 같다 — 질문 카드를 쓸 수 있다) | 항상 `"other"`(질문 도구를 붙이지 않는다 — 결정) |
| `mentionsEnabled`(1324) | `mentionDepth < mentionChainLimit` | **항상 true**(상한 없음, 결정) | **항상 false**(작업자는 못 부름, 결정) |
| 멘션 호출(1552-1559 자리) | `scheduleMentionReplies` | **아무것도 하지 않는다** — 작업자를 부르는 것은 여기가 아니라 §(4)에서 명시한 `runUnit`의 `finally`다(타이밍 문제, §(4) 참고) | 아무것도 하지 않는다(작업자는 §(4)에 따라 묶음으로만 시작한다). 다만 여기서는 `parseMentions(text, this.agents).filter(id => id !== agent.id)`가 비어 있지 않으면 한 줄 안내(결정: "작업자 턴의 @호출은 차단, 안내 한 줄") — `@${agent.id}가 다른 참가자를 부르려 했지만 작업자는 다른 참가자를 부를 수 없습니다. 필요하면 지휘 AI가 다음 회신에서 다시 맡길 수 있습니다.` 이 안내만은 **여기서** 낸다(작업자 자신의 턴이 끝나는 자리라 텍스트를 다시 읽을 필요가 없다). |
| `setAwaitingUser`(1565-1567, 끝 ASK_USER) | 조건 맞으면 세움 | **`runResponseTurn`에서는 부르지 않는다**(적대적 검토로 바꿈 — 아래 설명) | **세우지 않는다.** 대신 `controlRequest`를 결과 블록(§(7))에 적어 지휘 AI에게 전달한다. |
| `buildAgentPrompt`의 `parallel`(1315) | 조건대로 | 적용 안 됨(지휘 AI는 독립 발언 묶음 멤버가 아니다) | `context.parallelGroupId`를 안 쓰므로 항상 꺼져 있다(§(4)) |
| `buildAgentPrompt`의 `concurrentWork` | 조건대로 | 그대로(지휘 AI도 다른 돌고 있는 턴을 볼 수 있다) | 그대로(묶음 밖의 다른 턴만 — §(4)) |
| `extraLines`(새로 뺀 입력, 지금 `buildAgentPrompt`에 연결 안 돼 있음) | 없음 | `context.extraLines`(결과 블록 + 보류 메시지, §(7)) | 없음 |
| 프롬프트 역할 설명(§(11)) | "그룹 채팅 참가자" | 지휘 AI 전용 문단 | 작업자 전용 문단 |

**지휘 AI의 질문 카드는 그 라운드가 실제로 끝날 때만 선다**(적대적 검토로 고침). 지휘 AI 턴이 작업자를 더 부르면서 동시에 끝에 `ASK_USER`를 남기면, 원래 설계대로 `runResponseTurn`에서 바로 `setAwaitingUser`를 세우면 다음 회신 턴이 자동으로 claim될 때 `respond()`(1250-1255)가 무조건 `clearAwaitingUser`를 불러 카드를 사용자가 보기도 전에 지워버린다(작업자 묶음이 끝나는 데 보통 수십 초 걸리므로 "본 적 없이 사라지는 질문"이 된다). 그래서 지휘 AI 역할은 `runResponseTurn` 안에서 `setAwaitingUser`를 **아예 부르지 않고**, `controlRequest`를 outcome에 그대로 실어 돌려준다(모양은 이미 있다 — 새 필드 없음). 결정은 `runUnit`의 `finally`(§(4)의 공용 문을 지난 뒤)에서 내린다: §(4)·§(5)를 거쳐 **이 자리에서 오케스트레이션이 끝나는 것으로 판정되고**(작업자 후보가 0명이거나 안전선에 걸림) **동시에** `outcome.controlRequest?.action === "ASK_USER"`이면, 그제서야 `setAwaitingUser(leadId, ...)`를 부른다 — 이 경우는 다음 자동 회신 턴이 없으므로 카드가 안전하게 남는다. 작업자를 불러 오케스트레이션이 **계속되면** 그 질문은 결과 블록에도, 화면에도 올라가지 않고 조용히 버려진다(받아들이는 손실, §(15) — 지휘 AI가 작업을 맡기면서 동시에 사용자에게 묻는 것은 의미가 모호하므로, "맡기지 않고 끝맺을 때만 물을 수 있다"로 단순화한다).

`runResponseTurn`의 `buildPrompt` 호출에 `extraLines: context.extraLines || []`를 더하는 것이 유일하게 **모든 턴에 영향을 주는** 변경이다(기본값 `[]`이라 지금 턴은 결과가 같다 — `chat-prompt.js`가 이미 그 입력을 받아 두되 아무도 안 채워서 안 쓰던 것뿐이다).

## (7) 결과 수집과 한 번의 회신 턴

**모든 턴 결과가 지나는 한 곳**은 `runUnit`(chat-room.js:973)이 `Promise.all(members.map(item => this.runQueuedTurn(item)))`로 받는 배열이다(지금은 버려진다). §(4)에서 정한 대로 `unit.items[0].context.orchestration?.role === "worker"`이면 `runUnit`의 `finally`에서 **폴더 밖 변경 감시 대신** 이 배열로 결과 블록을 짓고 지휘 AI의 다음 턴을 잡는다.

`runQueuedTurn`이 돌려주는 `outcome`은 이미 아래 중 하나다(새 코드가 더 만들 것이 없다):

| outcome 모양 | 의미 | 결과 블록에 적는 문구 |
|---|---|---|
| `undefined` | 시작 전에 비활성·미설치로 걸러짐, 또는 세대가 바뀌어(중지) 버려짐 | "사용할 수 없음"(시작 전 거름) 또는 블록에 **안 적는다**(중지 뒤의 늦은 결과 — §8, 폐기) |
| `{ ok: false, stopReason, error, ... }` | 실패·한도·출력 제한 등 | `"실패(${stopReason}): ${error를 1000자로 clip}"` |
| `{ ok: true, controlRequest, text }`, `controlRequest?.action === "ASK_USER"` | 되질문으로 끝남 | `"질문 있음: ${controlRequest.question}"` + 보기 목록(있으면) |
| `{ ok: true, text }`, controlRequest 없음 | 정상 완료 | `${text를 2000자로 clip, 넘으면 "…(생략, 전체 N자)"}` |
| §(4)에서 시작 전에 걸러진 id(비활성·미설치) | | `"사용할 수 없음(비활성화되었거나 설치되지 않음)"` |

블록 모양(지휘 AI 프롬프트의 `extraLines`에 그대로 들어간다 — 대화창 메시지가 아니므로 압축에 잘리지 않는다):

```
=== 작업자 결과(라운드 N) ===
[@codex] 완료
<clip된 본문>
---
[@agy] 실패(TIMED_OUT)
<clip된 오류>
---
[@teamX] 사용할 수 없음(비활성화되었거나 설치되지 않음)
=== 작업자 결과 끝 ===
```

`orchestration.heldMessages`가 비어 있지 않으면 바로 이어서(같은 `extraLines` 안에):

```
=== 사용자가 그 사이 보낸 메시지 ===
"<메시지 1>"
"<메시지 2>"
=== 사용자가 그 사이 보낸 메시지 끝 ===
```

을 붙이고 `heldMessages`를 비운다. 지휘 AI 턴이 **실제로 claim될 때**(예약 때가 아니라) `this.messages`를 다시 읽어 확정한다 — 결정("그 사이에 끝난 결과를 모두 보고 시작")과 REPLY_NOW §2.6(시작 시점 기록)이 같은 원리다.

작업자 각자의 완료/실패 메시지는 평소처럼 `this.messages`에도 그대로 쌓인다(일반 턴과 다르지 않다 — 사용자도 대화창에서 작업자의 원문을 본다). 블록은 **그 메시지들이 `promptMessages`에서 걸러지거나(에러는 걸러진다, chat-room.js:1247) 압축에 밀려도** 지휘 AI가 반드시 보게 하는 여분의 통로다.

이 블록을 들고 지휘 AI의 다음 턴을 §(5)의 안전선 점검을 거쳐 `scheduleTurn(leadAgent, context, { lane: "fast" })`로 claim한다(`round += 1`, `context.orchestration = { id, role: "lead", round }`, `context.extraLines = [블록]`, `context.turnRootId`는 그대로 "오케스트레이션을 시작한 그 사용자 메시지"를 가리킨다 — 지휘 AI의 회신은 늘 원래 사용자 요청에 대한 답이라는 뜻이다). 지휘 AI가 이 턴에서 또 @작업자를 부르면 §(4)·§(5)가 반복되고, @ 없이 답하면 §(8)에서 끝난다.

## (8) 오케스트레이션이 끝나는 모든 경우

**끝내는 것(결정 6)**: 지휘 AI가 @ 없이 답함, 안전선(라운드·실행), 중지, 잠깐, 삭제, 종료, 재시작, 지휘 AI를 못 쓰게 됨, 모드를 끔(또는 지휘 AI를 바꿈), **오케스트레이션 턴을 ×로 지움**(아래, 새로 추가). 그 밖의 모든 것은 **끝내지 않는다.**

**공용 헬퍼 `endOrchestration(notice)`**(적대적 검토로 추가 — §(17)). 중지·잠깐·삭제·종료를 뺀 나머지 모든 "끝내는 것"(×취소, 모드 끔/지휘 AI 바꿈, 지휘 AI 못 쓰게 됨, 안전선, 지휘 AI가 @ 없이 답함)이 이 하나를 공유한다(중지·잠깐류는 `stopAllSilently`가 이미 큐 전체를 치우므로 아래에서 따로 설명한다). `this.orchestration`이 없으면 아무것도 하지 않는다. 있으면 순서대로:

1. **형제를 치운다**: `turnQueue`·`deferredTurnQueue`를 돌며 `item.context.orchestration?.id === this.orchestration.id`인 항목을 전부 `removeQueued` + `retireTurn(item, undefined, { lost: false })`한다(개별 유실 안내는 안 낸다 — 아래 3번의 안내 한 줄이 그 역할을 겸한다). 같은 묶음의 아직 claim 안 된 형제, 혹은 agent가 바빠 대기하던 작업자 묶음 전체가 여기서 사라진다 — 모드를 끄거나 ×로 지운 **뒤에** 그 담당자가 자유로워져도 죽은 오케스트레이션을 실행하지 않는 이유다.
2. **헬퍼를 부른 쪽이 넘긴 `notice` 문구**(없으면 아무 줄도 안 남긴다 — "지휘 AI가 @ 없이 답함"처럼 원래 안내가 없는 경우를 위해)에, `heldMessages.length > 0`이면 `"그 사이 보낸 메시지 N개는 지휘 AI에게 따로 묶어 전달되지 않았습니다(대화에는 그대로 남아 있습니다)."`를 이어붙인다(둘 다 있으면 공백으로 이어 한 줄, `notice`만 있으면 그것만, 둘 다 없으면 아무것도 안 낸다).
3. `this.orchestration = null`.
4. `this.resolveIdleWaiters()`(§2.4(b) — 반드시 3 다음, 그래야 토론이 기다리고 있었으면 깬다) → `this.pumpAfterTurn()`(1번에서 치운 자리 뒤의 메인 줄 머리가 풀렸을 수 있다) → `this.emitTurnStateSafe()`.

- **지휘 AI가 @ 없이 답함**: §(4)에서 실행 가능한 작업자가 0명이면(실제로 아무도 안 불렀거나, 부른 전원이 비활성·그룹 별칭·자기 자신이었으면) 그 턴이 오케스트레이션의 **최종 답**이다. `endOrchestration(null)`을 부른다(별도 안내는 없다 — 지휘 AI의 답 자체가 끝맺음이다. `heldMessages`가 있으면 2번 규칙대로 그 한 줄만 남는다) — 다만 비활성 id를 불렀다가 전부 못 썼으면 `endOrchestration("⟦그 id들⟧을 부를 수 없어 맡기지 못했습니다.")`.
- **안전선**: §(5)에서 설명한 대로, 멈춘 자리에서 `endOrchestration("실행 횟수 안전선(150회)에 닿아 더 맡기지 않았습니다. 메시지를 보내면 이어 갑니다.")` 또는 라운드 쪽 문구.
- **중지(stopAll)·잠깐(interject)**: `stopAllSilently`가 지금 하는 일(큐 비우기, 실행 중 턴 취소 요청, `runningTurns`는 프로세스가 끝날 때까지 유지)에 **`this.orchestration = null`을 더한다** — `endOrchestration`을 쓰지 않고 직접 둔다(이미 큐 전체를 치우므로 1번 단계가 중복이고, 2번의 "전달 안 됨" 안내도 불변식 10이 "필요 없다"고 정한 바로 그 경우다). 자리는 **반드시 기존의 `this.resolveIdleWaiters()` 호출(지금 코드 끝자락, 2049줄)보다 앞**이어야 한다(§2.4(b)). 대기 중이던 작업자 묶음·지휘 AI 회신 턴은 보통 턴처럼 `retireTurn(..., {lost: ...})`으로 버려진다(잠깐은 `notifyLost:false`로 한 줄에 합쳐 안내하는 지금 방식 그대로). **늦게 끝나는(취소했지만 아직 안 끝난) 지휘 AI·작업자 프로세스의 결과는 `runUnit`의 `finally`가 분기 맨 앞에서(§(4)의 공용 문) `this.orchestration`이 없거나 `id`가 다르면 역할과 무관하게 아무것도 짓지 않고 조용히 돌아간다**(폐기 — 중지 뒤의 늦은 결과는 결과 블록도, 새 지휘 AI 턴도 만들지 않는다. 실행이 이미 성공해 메시지를 남겼다면 그 메시지 자체는 지우지 않는다 — "메시지"와 "회신 턴을 여는 것"은 다른 일이다).
- **대화 삭제·앱 종료**: `stopAllSilently`를 거치므로 위와 같다. 종료는 §2.2에서 적은 안내 한 줄을 **먼저** 남긴다(`stopAllSilently`가 `liveRuns`를 기다리지 않고 즉시 돌지만, 안내 `appendMessage`는 그 전에 동기로 끝난다).
- **재시작**: `this.orchestration`은 휘발성이라 새 프로세스에는 처음부터 없다(§2.2) — "끝난" 것이 아니라 "존재한 적 없는 것"이 되지만 결과는 같다(이어가는 길 없음, 재시작 전 저장된 안내 한 줄만 남는다).
- **오케스트레이션 턴을 ×로 지움(`cancelTurn`)**: 지우려는 항목에 `context.orchestration`이 있으면(= 이미 claim돼 생긴 작업자 묶음의 아직-claim-전 형제, 또는 지휘 AI의 대기 중인 회신 턴) 그 한 항목만 지우는 지금의 일반 로직을 타지 않고 `endOrchestration("오케스트레이션을 여기서 끝냅니다. 지금까지의 결과는 위에 있습니다.")`을 대신 부른다(1번 단계가 그 항목 자신도 포함해 치운다 — 따로 지울 필요 없다). **아직 claim되지 않아 `context.orchestration`이 없는, 맡기기를 막 시작하는 턴**(§2.3의 `context.orchestrationStart`만 있는 상태)을 지우는 것은 **오케스트레이션이 아직 생기지 않았으므로** 지금의 일반 × 취소 그대로다(끝낼 오케스트레이션이 없다 — 가르는 기준은 `context.orchestration`뿐이고 `orchestrationStart`를 추가로 볼 필요가 없다). 화면은 오케스트레이션 턴의 대기 항목에 ×를 **그대로 보여준다**(숨기지 않는다 — "일반 모드로 돌아가는 길은 어떤 상태에서도 막히지 않는다"는 원칙이 ×에도 적용되어야 한다) — 다만 눌렀을 때 "작업자/지휘 AI 전체를 그만둡니다"로 이해되게, 툴팁을 보통 × 취소("…전달되지 않았을 수 있습니다")와 다르게 "오케스트레이션을 여기서 끝냅니다"로 바꾼다.
- **지휘 AI를 못 쓰게 됨(`setAgents`로 비활성·미설치)**: 지금 `runResponseTurn`은 턴 맨 앞에서 `findAgent`가 비면 `undefined`를 조용히 돌려준다(1260) — 오케스트레이션의 지휘 AI 턴(다음 회신 턴 포함)에서 이 일이 나면 **조용히 두지 않는다**: `runUnit`의 `finally`(§(4) 공용 문을 지난 뒤, lead 분기)가 "결과가 `undefined`(세대 불일치가 아닌, 에이전트 자체가 사라진 경우)"를 보면 `endOrchestration("@지휘AI를 더 쓸 수 없어 오케스트레이션을 끝냅니다. 지금까지의 결과는 위에 있습니다.")`. 세대 불일치로 인한 `undefined`(중지)는 위 중지 경로가 이미 처리하므로 중복 안내가 나지 않게, 이 검사는 `generation === this.generation`일 때만 한다.
- **모드를 끔(IPC `chat:orchestrator:set { enabled:false }`) 또는 지휘 AI를 바꿈**: IPC 핸들러가 `room.orchestration`이 있으면 `room.endOrchestration("오케스트레이터 모드를 꺼서 오케스트레이션을 끝냅니다. 지금까지의 결과는 위에 있습니다.")`(지휘 AI를 바꾸는 경우는 같은 문구를 "지휘 AI를 바꿔서…"로)을 부르고 메타를 저장한다. **진행 중인 작업자 프로세스는 중지하지 않는다** — 흐름이 끝났다는 것과 떠 있는 프로세스를 죽이는 것은 다른 일이다(지금 중지/잠깐만 프로세스를 끊는다는 원칙과 같다). 그 결과가 돌아와도(지휘 AI 자신의 회신 턴이 돌고 있었던 경우 포함) `runUnit`의 `finally`는 §(4)의 공용 문에서 바로 걸러 아무것도 짓지 않는다 — 다만 그 작업자(또는 지휘 AI)의 답은 메시지로는 남는다.

**끝내지 않는 것(결정 6, §(3) 라우팅표와 같다)**:

- **직접 @other(지휘 AI 아닌 특정 AI) 메시지**: 오케스트레이션을 건드리지 않는다. 그 AI가 지금 작업자로 바쁘면 "그 작업을 끝낸 뒤 이어서 답한다"는 바로 답하기의 담당자 게이트가 그대로 해 준다(§(4)의 "교차점" 수정만 있으면 새 코드가 필요 없다). 이 답 자체는 오케스트레이션의 일부가 **아니다**(보통 자유 대화 턴 — 결과 블록에도 안 들어가고, 지휘 AI도 이 대화를 모른다. 다음 회신 턴의 대화 기록에는 보통 메시지로 보이긴 하지만 결과 블록처럼 짚어 주지는 않는다. §(15) 위험으로 적는다).
- **지휘 AI에게 가는 메시지(@ 없음·@지휘AI만)**: §(3)에서 "보류"로 분류되어 턴을 만들지 않는다. `orchestration.heldMessages.push(text)`만 하고, **메시지마다** 한 줄 안내를 낸다:
  - 보통: `"결과가 모이면 이 메시지까지 보고 이어 갑니다. 지금 바로 바꾸려면 [잠깐]을 누르세요."`
  - 지휘 AI가 질문 카드를 기다리는 중이면: `"@지휘AI가 질문 카드에 답을 기다리는 중입니다. 이 메시지는 그 카드에 답하거나 건너뛴 뒤, 다음 회신에 함께 전달됩니다."`
  - 같은 라운드에 메시지를 두 번 이상 보내면 매번 안내가 나오고, 모두 `heldMessages`에 쌓여 **다음 한 번의** 회신 턴에 함께 들어간다(결정의 "사용자가 그 사이 보낸 메시지" 묶음, §(7)).
  - "지금 바로 바꾸기"는 잠깐(§8의 중지/잠깐 경로)뿐이다 — 이 메시지 자체로는 아무것도 바뀌지 않는다(결정).
- **그룹 별칭(@all 등)**: §(0) 비판 검토에서 정한 대로 늘 그대로 모두에게 가고 오케스트레이션은 그대로 간다.
- **승인 카드 대기(지휘 AI 또는 작업자 쪽)**: 그 턴은 `runningTurns`에 남아 있을 뿐이고 오케스트레이션 상태는 그대로다. 화면에 "오케스트레이터 일시 정지"가 보인다(§(9)).

## (9) 일시 정지 표시

`meta.permissionMode`가 `workspace-write`이고 자동 승인이 꺼져 있을 때 지휘 AI 또는 작업자 턴이 `pendingApprovals`에 걸려 있으면(기존 승인 카드 메커니즘, 바뀌지 않는다) 화면의 오케스트레이터 상태 줄이 "라운드 N · 실행 M" 대신(또는 그 옆에) "일시 정지(승인 대기)"를 보인다. 질문 카드는 지휘 AI 자신의 것만 있을 수 있으므로(작업자에겐 질문 도구를 안 붙인다, §(6)) 같은 표시가 "일시 정지(질문 대기)"로도 쓰인다.

**검증에서 고침(review-behaviour, major)**: 처음 구현은 "지휘 AI 또는 작업자 턴이"라는 scope를 실제로는 안 지켰다 — `pendingApprovals`/`userQuestions`를 `sessionId`만으로 걸러, **이 방의 무관한 곁가지 대화**(예: 오케스트레이션과 나란히 도는 직접 `@other` 턴, §(8) "직접 @other")가 승인·질문을 기다려도 "일시 정지"가 잘못 켜졌다. 고침: `orchestrationSnapshot()`이 `agentIds`(지휘 AI + 지금 이 오케스트레이션으로 claim된 작업자 id들, `liveTurns()`에서 `context.orchestration.id` 일치로 추린다)를 함께 내려 주고, 렌더러는 `approval.agentId`/`question.agentId`가 그 집합에 있을 때만 "일시 정지"를 켠다(`src/chat/chat-room.js`의 `orchestrationSnapshot`, `src/chat.js`의 `renderOrchestrationStatus`). `agentIds`는 상태 줄에 그리지 않는다(§(5) "화면엔 라운드·실행 횟수만"은 그대로 — scope 계산에만 쓰는 내부 값이다).

두 표시 모두 `room.state()`의 `orchestration.{round,executions}` 필드 자체는 바꾸지 않고, 이미 있는 `pendingApprovals`/`userQuestions` 스냅숏 + 위 `agentIds`에서 렌더러가 계산한다(새 방 상태 불필요).

## (10) "AI끼리 계속 부르기"(keepCalling)

이 체크는 **오케스트레이션이 전혀 건드리지 않는** 보통 멘션 연쇄(§(1)의 "에이전트 답 속 @멘션")에만 적용된다 — 지휘 AI·작업자 턴은 `context.orchestration`이 있어 처음부터 `scheduleMentionReplies`를 타지 않으므로(§(6)) 이 체크는 그 경로에 **도달조차 하지 않는다**(그래서 "지휘 AI·작업자 호출에는 효과 없음"이 코드 한 줄 분기 없이 성립한다 — §0). 다만 "효과 없음"은 **거기까지만**이다 — 오케스트레이션 중에도 §(3)의 "직접 @other" 곁가지 대화는 자유롭게 돌고, 그 대화의 답이 또 다른 AI를 @로 부르면 그건 보통 멘션 연쇄라 이 체크가 **그대로 적용된다**. 그래서 화면은 오케스트레이터가 켜져도 체크를 **흐리게 그리지 않는다**(2차 적대적 검토로 바뀐 기본값, §0) — 대신 툴팁에 적용 범위를 적는다.

`this.mentionCallCounts`(Map, `turnRootId`(연쇄를 처음 일으킨 사용자 메시지 id) → 지금까지 만든 자동 호출 수)를 새로 둔다. `scheduleMentionReplies(agent, text, depth, attachments, turnRootId)`:

1. `mentionsMuted`면 지금처럼 아무것도 안 한다(잠깐은 keepCalling과 무관하게 항상 이긴다).
2. `!this.meta.keepCalling && depth >= this.mentionChainLimit`이면, **지금처럼 멈추되** 걸러진 멘션 id가 하나라도 있으면 한 줄 안내를 낸다(지금은 조용히 버림 — 결정으로 바뀌는 부분): `"@a, @b 호출이 전달 상한(2)에 걸려 전달되지 않았습니다. 계속 이어 가려면 입력창 위 'AI끼리 계속 부르기'를 켜세요."` 안내는 **이 답 하나당 한 번**(여러 멘션이 한꺼번에 걸려도 한 줄).
3. `this.meta.keepCalling`이면 depth 상한을 보지 않는다. 대신 `mentionCallCounts.get(turnRootId) || 0`이 50 이상이면, 아직 안내하지 않았으면(루트마다 한 번) `"이 메시지에서 이어진 자동 호출이 50번에 닿아 멈췄습니다. 메시지를 보내면 이어 갑니다."`를 내고 더 이상 호출을 만들지 않는다. 50 미만이면 멘션마다 호출을 만들며 카운터를 올리고, 루프 중간에 50을 넘으면 그 순간부터(이 답의 나머지 멘션 포함) 막는다.
4. 그 밖은 지금과 같다(자기 자신 제외, 비활성·미설치 제외).

카운터는 `turnRootId` 단위라 **갈래가 퍼져도 합계로 막는다**(결정 그대로 — 두 갈래가 각각 30번씩 불러도 합계 60에서 멈춘다). 중지·잠깐·새 사용자 메시지(새 `turnRootId`)는 새 카운터로 시작한다(`mentionCallCounts`는 지워도 되고 안 지워도 된다 — 새 루트는 항상 새 키이므로 맵이 자라는 것만 신경 쓰면 된다. `stopAllSilently`에서 비운다, 메모리 누수 방지).

## (11) 프롬프트

**모든 보통 턴의 프롬프트는 한 글자도 바뀌지 않는다**(§(6) 표의 분기는 `context.orchestration`이 있을 때만 켜진다). 지휘 AI·작업자 프롬프트는 `buildAgentPrompt`에 새 입력을 더하지 않고 **기존 분기를 재사용**한다: 지휘 AI/작업자는 `discussion`도 `discussionSummary`도 `simplifyMeta`도 아닌 **보통 자유 대화 턴**이고, 위 (6)의 `mentionsEnabled`·`extraLines`·`concurrentWork`만 다르다. 역할 설명 문단만 새로 추가한다(기존 "그룹 채팅 참가자" 문단 자리, chat-prompt.js:140-165의 `else` 분기 **안**에 조건을 더 넣는다):

**지휘 AI 턴에 더하는 줄(역할 설명 문단 맨 앞)**:
- "당신은 @{agent.id}, 이 방의 지휘 AI입니다. 사용자 요청을 보고, 필요하면 아래 참가자에게 작업을 나눠 맡기세요: {작업자 후보 목록}."
- "@이름으로 부르면 그 참가자가 이번 라운드에 당신과 **별도로** 작업을 시작합니다. 한 번에 여러 명을 불러도 됩니다 — 같이 시작합니다."
- "각자에게 맡기는 내용은 **그 사람 혼자 보고 끝낼 수 있게 분명하게** 적으세요(서로의 질문을 못 듣습니다). 여러 명을 같이 부를 때는 겹치지 않게 서로 다른 파일·자료를 맡기세요."
- "맡긴 작업의 결과(성공·실패·질문 포함)는 다음 당신의 차례에 자동으로 모여서 옵니다. 실패나 질문이 있으면 당신이 판단해 다시 맡기거나 사용자에게 설명하세요."
- "할 일을 다 맡겼거나 더 맡길 필요가 없으면, **@ 없이** 사용자에게 바로 답하세요. 그 답이 사용자가 보는 최종 답입니다."
- (그 뒤로는 기존 "다른 참가자를 호출하려면…" 줄 대신 지휘 AI 전용 두 줄이 들어가므로, `mentionsEnabled` 분기(157-165)에서 `context.orchestration?.role === "lead"`일 때 이 문단 전체로 **대체**한다 — 상한 문구("호출은 꼭 필요할 때만")는 지휘 AI에겐 안 맞으므로 뺀다.)

**작업자 턴에 더하는 줄**:
- "당신은 @{agent.id}, 지휘 AI @{leadId}가 이번 라운드에 맡긴 일 하나를 처리합니다. 다른 참가자를 부르거나 사용자에게 직접 묻지 마세요 — 결정이 필요하면 응답 끝에 ASK_USER로 남기면 지휘 AI에게 전달됩니다."
- "맡은 일만 간결하게 처리하고, 당신의 답이 그대로 지휘 AI에게 전달됩니다."
- 끝 ASK_USER 계약은 쓰되(`userQuestionTool`은 항상 꺼져 있다 — §(6), 작업자가 되물을 유일한 길이다), **문구 두 군데를 작업자용으로 바꿔 쓴다**(적대적 검토 — 기존 문구 그대로면 "사용자에게 직접 묻지 마세요"와 "이건 사용자의 결정"이 한 프롬프트에서 서로 다른 말을 한다). `chat-prompt.js`의 `!discussion` 분기(166-174줄)에서 `context.orchestration?.role === "worker"`일 때 두 문장을 이렇게 바꾼다:
  - "맡은 작업을 이어가려면 **지휘 AI의 판단**이 꼭 필요할 때만, 응답 **맨 끝**에 `ASK_USER: <질문 한 줄>`을 붙이세요."(나머지 OPTION/MULTI 설명은 동일)
  - "제어 줄은 화면에 보이지 않고, **지휘 AI에게 전달되어 다음 회신 턴에서 판단됩니다**(사용자에게 직접 묻는 것이 아닙니다)."
  일반 턴·지휘 AI 턴(`role` 없음·`"lead"`)의 문구는 그대로 둔다 — 지금 문구가 그 둘에는 맞다.

지휘 AI가 **맡긴 지시 본문**(= 지휘 AI 자신의 답 전체)은 별도 블록으로 짜지 않는다 — `context.turnRootId`를 지휘 AI 답의 메시지 id로 두므로, 작업자 턴의 대화 기록(`promptMessages`)이 claim 시점까지의 전체 대화를 보여주고 그 **마지막 메시지가 바로 지휘 AI의 지시**다(REPLY_NOW §2.6의 "마지막 메시지에 이어 답하라" 문구가 자연히 맞는 경우라 `replyTarget`도 필요 없다 — 다른 작업자가 먼저 끝나 그 사이에 지휘 AI의 **다음** 턴이 섞여 들어올 일은 없다: 지휘 AI의 다음 턴은 이 묶음이 전부 끝난 뒤에만 claim된다). **일부러 하지 않는 것**: 지휘 AI의 한 답 안에서 "이 문단은 @codex, 저 문단은 @agy"처럼 자동으로 나눠 보내는 일. 모든 작업자가 지휘 AI의 **답 전체**를 함께 읽는다 — 자기 몫을 가려내는 것은 지휘 AI가 글을 명확히 쓰는 데 맡긴다(위 지휘 AI 프롬프트의 "분명하게 적으세요" 문장이 그 책임을 진다). 이유는 §(15)에 적는다.

**중립화**: 지휘 AI·작업자 문단에 "코딩"이라는 말을 쓰지 않는다("작업", "일", "참가자"로 충분하다) — 연구·기획 방에서도 그대로 읽히게 한다.

## (13) 불변식 (속성 시험 대상)

1. **단독 오케스트레이션**: 한 방에 `this.orchestration`은 한 번에 하나뿐이다(null이거나 하나). `isIdle()`은 `this.orchestration === null`도 봐야 한다. 양방향으로 막는다 — 오케스트레이션이 있으면 `startDiscussion`이 맨 앞에서 즉시 거절하고(`discussionRequested`를 건드리기 전, §2.4(a)), 토론이 요청·진행 중이면(`discussionRequested || discussionActive`) §2.3의 claim 시점 조건이 새 오케스트레이션을 만들지 않는다. 그래서 `discussionRequested`가 true인 어느 순간에도 `this.orchestration`은 null이고, 오케스트레이션 턴(항상 빠른 줄)의 `scheduleTurn` 호출이 `discussionRequested` 때문에 메인 줄로 떨어지는 일은 없다.
2. **라운드·실행 단조증가, 안전선 선점검**: `round`·`executions`는 오케스트레이션이 사는 동안 내려가지 않는다. 묶음·회신 턴을 **시작하기 전**에 늘어날 값이 상한을 넘는지 보고, 넘으면 시작하지 않는다(이미 시작한 턴은 끊지 않는다).
3. **작업자는 못 부른다**: `role === "worker"`인 턴의 `mentionsEnabled`는 항상 false이고, 그 턴이 끝난 뒤 새 턴이 생기지 않는다(멘션이 있었으면 안내 한 줄만 남는다).
4. **지휘 AI만 상한 없이 부른다**: `role === "lead"`인 턴은 `mentionChainLimit`을 보지 않는다.
5. **작업자는 서로를 못 본다**: 같은 묶음의 작업자 턴 프롬프트에는 서로의 답이 없다(`context.independent`로 REPLY_NOW §2.6 필터 재사용).
6. **묶음 일관성**: 한 번의 지휘 AI 답이 부른 작업자는 전부 같은 묶음(`workerUnitId`)으로 같이 claim된다. 같은 id를 두 번 불러도 작업자 턴은 하나다. `scheduleWorkerUnit`은 작업자들을 스케줄하는 동안 `pumpSuspended`로 펌프를 미뤄 두 번째 이후 작업자가 큐에 오르기 전에 첫 작업자가 혼자 claim되는 일이 없다(§(4)).
7. **결과 누락 없음**: 작업자 묶음이 끝나면(성공·실패·한도·미설치·건너뜀·질문 전부) 그 수만큼의 항목이 결과 블록에 있다(시작 전에 걸러진 비활성 id도 포함). 블록 없이 지휘 AI 턴이 다시 서지 않는다.
8. **한 번의 회신**: 작업자 묶음 하나가 끝날 때마다 지휘 AI 턴은 정확히 한 번만 새로 claim된다(둘 이상의 회신 턴이 겹쳐 돌지 않는다 — 바로 답하기의 담당자 게이트가 지휘 AI 자신에게도 적용되므로 저절로 성립한다).
9. **진행 중인 일은 사라지지 않는다**: 오케스트레이션이 진행 중일 때 온 어떤 사용자 메시지(직접 @other, 지휘 AI에게, @all)도 지휘 AI·작업자의 대기·실행 중 턴을 걷어내거나 취소하지 않는다(§(4) "교차점" 수정이 지키는 것). 오케스트레이션을 끝내는 것은 §(8)에 나열된 사건뿐이다.
10. **보류 메시지는 잃지 않는다**: `heldMessages`에 들어간 메시지는 그 오케스트레이션이 정상적으로(안전선 포함) 끝나는 그 순간까지 지워지지 않고, 다음 회신 턴의 `extraLines`에 정확히 한 번 들어간다. 중지·잠깐으로 끝나면(§8) 지워져도 안내가 이미 나갔으므로 유실 안내는 따로 필요 없다. ×취소·모드 끔·지휘 AI 못 씀·안전선으로 끝나면(사용자가 그 끝을 직접 고른 것이 아니므로) `endOrchestration`의 안내 한 줄에 "그 사이 보낸 메시지 N개는 지휘 AI에게 따로 묶어 전달되지 않았습니다"를 반드시 덧붙인다(§(8)).
11. **폐기**: 끝난(또는 바뀐) 오케스트레이션의 늦은 작업자 결과는 결과 블록을 만들지 않고, 지휘 AI의 새 턴을 claim하지 않는다.
12. **정리**: 중지·잠깐·삭제·종료·모드 끔 뒤 `this.orchestration`은 null이고, `mentionCallCounts`는 비었고(중지·잠깐·삭제), 떠 있던 승인·질문 대기는 보통 경로로 정리된다(§(8)에서 더하지 않은 것 — 기존 `stopAllSilently` 보장을 그대로 믿는다).
13. **실패는 조용하지 않다**: 지휘 AI 쪽의 실패(불가용·안전선·비활성)는 모두 한 줄 안내를 남긴다. 작업자 쪽의 실패는 안내 없이 결과 블록으로만 전달된다(그것이 "작업자 질문은 지휘 AI가 먼저 받는다"는 결정이 뜻하는 조용함이다 — 사용자에게 조용한 것과 시스템이 놓치는 것은 다르다).
14. **× 는 부분적이지 않다**: 대기 중인 지휘 AI 회신 턴이나 작업자 묶음 항목을 ×로 지우면 그 오케스트레이션 전체가 끝난다(§(8)) — 나머지 항목만 남아 묶음이 영영 안 끝나거나 `this.orchestration`이 안 풀리는 상태는 없다.
15. **폐기는 역할을 가리지 않는다**(적대적 검토로 추가): `runUnit`의 `finally`는 lead/worker로 가지치기 **전에** `this.orchestration?.id === unit.items[0].context.orchestration.id`를 확인한다(§(4)). 다르면 역할과 무관하게 아무것도 짓지 않는다 — 모드 끔·×취소가 지휘 AI의 회신 턴이 **도는 중에** 와도, 그 턴이 끝났을 때 죽은 오케스트레이션으로 작업자를 새로 부르지 않는다.
16. **메인 줄은 오케스트레이션에 굶지 않는다**(적대적 검토로 추가): `pumpPass`의 메인 줄 시작 조건은 "활성 단위가 전부 오케스트레이션 턴"이면 충족된다(§2.4(c)) — 오케스트레이션이 라운드를 도는 동안에도 `@all`·그 밖의 메인 줄 메시지가 오케스트레이션이 끝날 때까지 기다리지 않는다.
17. **지휘 AI의 질문은 라운드가 끝날 때만 선다**(적대적 검토로 추가): 지휘 AI 턴이 작업자를 불러 오케스트레이션이 계속되면, 그 턴 끝의 `ASK_USER`는 화면에 올라가지 않는다(§(6)) — 다음 자동 회신 턴이 곧바로 그 카드를 지워버릴 것이므로, 아예 세우지 않는 쪽을 택했다(받아들이는 손실, §(15)).

## (14) 시나리오 표

에이전트는 claude(지휘 AI로 고른다)·codex·agy, 러너는 약속을 손으로 푼다. "클레임"은 `claimUnit`이 그 턴을 `runningTurns`에 넣는 순간이다.

| # | 상황 | 사용자/에이전트 동작 | 기대 결과 |
|---|---|---|---|
| O1 | 오케스트레이터 켜짐(지휘=claude), 평범한 대화 | `@claude 이거 조사해줘` | claude가 보통 규칙대로(바로 답하기 포함) 턴을 받는다. claude가 @ 없이 답하면 끝(오케스트레이션이 생겼다 사라진다). |

## (15) 위험과 일부러 하지 않는 것

**받아들이는 위험**

- **지휘 AI가 작업을 쪼개는 글을 못 쓰면 작업자가 헷갈린다.** 지시를 자동으로 분배하지 않고 지휘 AI의 답 전체를 모든 작업자에게 그대로 준다(§(11)). 지휘 AI 프롬프트의 "분명하게 적으세요"가 유일한 완화책이다. 더 정교하게 쪼개려면(예: @멘션 뒤 문단만 그 작업자에게) 자연어 경계를 안정적으로 못 끊어 더 깨지기 쉬운 코드가 된다 — 하지 않는다.
- **동시에 도는 작업자의 파일 충돌.** 폴더 잠금·자기 폴더 전용 계약을 쓰지 않으므로(결정) 같은 파일을 둘이 고치면 나중 쓰기가 이긴다. 지휘 AI 프롬프트의 "서로 다른 파일을 맡기라"가 유일한 완화책이고 강제하지 않는다(REPLY_NOW가 바로 답하기 동시 실행에서 이미 받아들인 것과 같은 성격의 위험).
- **직접 @other 응답이 지휘 AI 모르게 진행된다.** 지휘 AI는 그 사이 벌어진 "곁가지 대화"를 모른 채 회신한다(결정이 요구하는 것은 "그 사이 끝난 **결과**"까지지, 모든 자유 대화가 아니다). 다음 회신 턴의 대화 기록에는 보통 메시지로 보이지만 결과 블록처럼 짚어 주지 않는다 — 사용자가 필요하면 직접 알려야 한다.
- **보류된 메시지가 쌓여도 화면에 상시 표시가 없다.** 메시지마다 안내 한 줄은 나가지만, "보류 중 N개" 같은 지속 표시는 이번 설계에 없다(§0). 라운드가 50까지 길어질 수 있으므로 사용자가 안내를 놓치면 꽤 오래 잊힐 수 있다 — 필요해지면 별도 과제.
- **지휘 AI 자체가 사용량 한도로 멈추면.** 지휘 AI의 회신 턴이 `rateLimited`로 실패하면 보통 자유 대화 실패와 같이 처리된다(실패 메시지 + `endOrchestration`, §(8) "지휘 AI를 못 쓰게 됨"과 구분 없이 같은 길로 끝난다 — 재시도 전용 경로는 두지 않는다. 사용자가 메시지를 다시 보내 오케스트레이션을 새로 시작하면 된다).
- **보류된 메시지가 곁가지 대화 상대에게는 "자기에게 온 말"처럼 보인다.** `heldMessages`에 쌓인 메시지도 `this.messages`에는 보통 사용자 메시지로 그대로 쌓인다(§(8) — 대화 기록에서 사라지면 안 되므로). 그래서 그 사이에 직접 `@other`로 대화하던 다른 에이전트가 자기 턴의 대화 기록을 읽을 때 이 메시지를 "지휘 AI 아닌 자신에게 말 건 것"으로 오인할 수 있다(실은 지휘 AI에게 보낸 것이 보류된 것뿐이다). 메시지를 숨기거나 꼬리표를 달면 지휘 AI의 `extraLines` 블록과 대화 기록이 다른 글이 되어 더 복잡해지므로, 이번 설계에서는 받아들인다.
- **안전선에 닿으면 마지막 라운드의 @지시가 그냥 버려진다.** "멈추고 안내"(계획 문구 그대로)를 택했다 — 멈추기 직전에 지휘 AI에게 "결과로 마무리 답을 하라"고 한 번 더 시키는 안(더 매끄러운 마무리)도 검토했지만, 가짜 추가 턴을 합성하는 코드가 더 생기고 계획 문구("닿으면 멈추고 안내")를 넘어서는 일이라 더 단순한 쪽을 택했다. 사용자가 안내를 보고 다시 말을 걸면 그 결과를 지휘 AI가 자연히 이어받는다(이미 결과 블록에 들어가 있던 것은 사라지지 않았으므로).
- **지휘 AI가 같은 답에서 작업자를 부르면서 동시에 끝 ASK_USER로 사용자에게 물으면, 그 질문은 버려진다.**(적대적 검토로 찾음) §(6)에서 정한 대로 지휘 AI의 질문 카드는 그 라운드가 작업자 호출 없이 끝날 때만 선다 — 다음 자동 회신 턴이 곧 그 카드를 지워버릴 것이므로 아예 세우지 않는 쪽을 택했다(O27). 지휘 AI 프롬프트가 "맡기지 않고 끝맺을 때만 ASK_USER를 쓰라"고 더 분명히 적도록 할 수도 있지만, 모델이 그 구분을 늘 지킨다고 보장할 수 없어 설계로 막는다.
- **`claimUnit`에 오케스트레이션 id 가드를 따로 두지 않는다.**(적대적 검토가 제안했으나 기각) `endOrchestration`의 큐 치우기(§(8))가 끝나는 모든 경로에서 동기·원자적으로 도므로(JS 단일 스레드, 중간에 끼어들 틱이 없다) 큐에 죽은 오케스트레이션 항목이 남아 `claimUnit`에 도달하는 창이 코드 구조상 없다. 혹시 몰라 가드를 하나 더 두는 것은 그 창이 실제로 없다는 것을 알면서 방어 코드를 쌓는 것이라 하지 않는다 — `runUnit`의 `finally` 맨 앞(§(4))에 두는 공용 문(이미 claim돼 돌고 있는 항목을 위한 것)과 역할이 다르다.
- **지휘 AI에게 가는 메시지가 스케줄되고 claim되기 전 좁은 창에서 토론이 요청되면, "맡기기"가 조용히 보통 대화가 된다.**(적대적 검토로 찾음) §2.3·§2.4(a)의 방어적 조건(`!discussionRequested && !discussionActive`)이 막아 오케스트레이션이 토론과 동시에 서는 일은 없지만, 그 대신 사용자가 "맡겼다"고 생각한 메시지가 지휘 AI의 보통 답 하나로 끝난다. claim 시점에 한 줄 안내를 내 조용히 넘어가지 않게 한다(§2.4(a)).

**일부러 하지 않는 것**

- 작업자 사이의 직렬 실행(v4 §2-11은 직렬이었지만 v5가 동시 실행으로 바꿨다 — REPLY_NOW의 단위 기계를 그대로 쓴다).
- 작업자가 사용자에게 직접 묻는 길. 작업자의 질문은 항상 결과 블록을 거쳐 지휘 AI에게만 간다.
- 지휘 AI 지시를 참가자별로 쪼개는 파서.
- 오케스트레이션 상태의 영속화·재시작 뒤 이어가기.
- 사용자가 라운드·실행 상한을 설정하는 화면(결정: 없음).
