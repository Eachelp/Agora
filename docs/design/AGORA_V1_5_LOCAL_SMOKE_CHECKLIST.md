# Agora V1.5 로컬 실행 체크리스트

V1.5(Handoff-aware Professional FSM)는 자동 테스트 1,400여 건과 페이크 러너
가상 실행으로만 검증됐다. 이 문서는 실제 Electron 앱과 실제 CLI 에이전트로
돌려 볼 시나리오와, 각 시나리오에서 **무엇이 보여야 정상인지**를 적는다.
2차 코드 리뷰에서 고친 변경점(§9)은 시나리오 안에 ★로 표시했다.

## 0. 준비

- `git pull origin main` → `npm install` → `npm start`.
- CLI 3종(claude / codex / gemini) 인증 상태를 설정 화면에서 확인한다.
  시나리오 ⑥-2는 그중 하나를 일부러 로그아웃한 상태로 쓴다.
- 프로젝트를 만들고 **워크스페이스 폴더**를 지정한다(git 저장소면 checkpoint
  동작까지 볼 수 있다). 권한은 **워크스페이스 쓰기**.
- 프로젝트 기록 → 전문 모드 역할 설정에서 기획·검토·구현 담당자를 서로
  다른 CLI로 지정한다(기획 검수는 비워도 된다 → 검토 담당자가 맡는다).
- Journal 파일: `~/.agora/sessions/<세션id>/professional-events.jsonl`
  (Windows는 `%USERPROFILE%\.agora\sessions\...`). 시나리오마다 아래로 확인한다.

  ```bash
  tail -n 30 ~/.agora/sessions/<세션id>/professional-events.jsonl
  ```

- 이상이 있으면 다음을 함께 남긴다: 시나리오 번호, 화면의 시스템 메시지
  원문, Journal 마지막 30줄, 문제가 된 역할의 **원문 응답**(제어 줄이 어떻게
  붙어 있었는지가 핵심이다).

## ① PLAN → NEEDS_DECISION → 답변 재개

1. 헤더의 일반/전문 스위치를 **전문**으로 켠다.
2. 결정이 필요한 요청을 보낸다. 예: `로그인 기능 만들어줘. DB는 아직 안 정했어.`
3. **PLAN** 클릭.

기대:
- 기획자가 `STATUS: NEEDS_DECISION`으로 멈추고, 시스템 메시지
  `역할이 사용자 결정을 요청했습니다: <질문>`이 보인다. 기획자 본문에는
  `ASK_USER:` 줄이 남아 있지 않다.
- 컴포저 버튼이 **답변 보내기**로 바뀐다. ★ 질문에 인라인 백틱(`` `strict` ``
  같은)이 있어도 그 부분이 비어 있지 않다.
- 답변을 보내면 기획자가 이어서 `PLAN_READY`를 내고 기획 검수 → READY
  (**실행 ▶** 활성)까지 간다. 재개된 기획자 답변이 자기 질문의 맥락을 알고
  있어야 한다(질문을 다시 묻지 않는다).
- Journal: `USER_DECISION_REQUIRED` → `USER_DECISION_RECEIVED`. 기획자가
  `HANDOFF: @reviewer`를 붙였다면 `HANDOFF_REQUESTED` → `HANDOFF_ACCEPTED`
  (`role: "reviewer"`, `reason` 필드가 채워짐).

## ② 전체 실행 ⚡ — Handoff 루프와 Archivist

1. 작은 작업을 요청한다. 예: `README에 설치 절을 하나 추가해줘.`
2. 자동 보완 체크박스 둘 다 켠다(기획 2회, 구현 1회 기본값).
3. **전체 실행 ⚡** 클릭.

기대:
- 진행 표시가 기획 ─ 기획검수 ─ 구현 ─ 구현검수 ─ 기록 순으로 넘어간다.
- 완료 뒤 검토자가 `HANDOFF: @recorder`를 붙였다면
  `검토자의 요청으로 기록 정리(Archivist)를 시작합니다`가 나오고, **기록
  정리** 역할 배지가 붙은 응답이 하나 더 온다. ★ 그 응답은 "앞 대화에
  이어" 답하는 잡담이 아니라 Journal·변경 요약을 근거로 한 정리 형태다.
- 각 역할 응답 본문에 `HANDOFF:` / `COMPLETE` / `PURPOSE:` / `REASON:` 줄이
  남아 있지 않다(질문 두 개처럼 모호한 제어는 예외 — 그대로 남긴다).
- ★ 구현자 응답이 diff 코드펜스 뒤에 제어 줄을 붙였다면 펜스가 온전히
  보인다. 제어 줄 **뒤에** 펜스가 이어졌다면 제어 줄이 본문에 그대로 남고
  펜스는 지워지지 않는다(이 경우 그 Handoff는 수용되지 않고 기본 흐름으로
  진행되는 것이 정상).
- Journal: `ROLE_STARTED`/`ROLE_FINISHED`가 단계 순서대로, `REVIEW_VERDICT`,
  `RUN_COMPLETED`, 마지막에 `ROLE_STARTED`(`purpose: "archivist"`).
  정상 흐름에서 `HANDOFF_REJECTED`가 나오면 `reason` 값과 함께 보고한다.

## ③ 구현검수 FIX_REQUIRED → 자동 보완 → PASS

1. 검토자가 한 번은 `FIX_REQUIRED`를 낼 만한 요청을 쓴다. 예: 요구사항에
   `기존 테스트가 모두 통과해야 함`을 넣고 테스트를 깨기 쉬운 변경을 시킨다.
2. 구현 자동 보완을 **3회**로 올리고 **전체 실행 ⚡**.

기대:
- `구현 보완` 라운드가 돌고 PASS까지 간다. ★ 보완이 여러 번 돌아도
  `역할의 HANDOFF 요청을 수용하지 않았습니다(HANDOFF_BUDGET_REACHED)`가
  나오지 않고, 마지막 Archivist 요청이 유실되지 않는다.
- 검토자가 계획 자체의 문제로 `HANDOFF: @planner`를 붙이면 재기획 안내와
  함께 BLOCKED 후속 모달(**변경 유지 후 재기획** / **작업 전 복원 후 재기획**)
  이 열린다.
- Journal: `REVIEW_VERDICT`(FIX_REQUIRED) → `ROLE_STARTED`(implementation) →
  … → `REVIEW_VERDICT`(PASS). `HANDOFF_REPEAT` 거부가 보이면 보고한다.

## ④ '@팀 실행' → READY 게이트

1. 채팅에 `@팀 실행 설정 파일 검증 로직 추가해줘`를 보낸다.

기대:
- `팀 자율 실행을 시작합니다: 기획 → 기획 검수가 자동으로 진행되고, 구현
  시작 전 승인 대기에서 멈춥니다.` 뒤에 기획·기획검수만 자동으로 돈다.
  구현은 **실행 ▶**를 눌러야 시작된다.
- 워크스페이스가 없는 세션에서 같은 문장 →
  `팀 자율 실행을 시작하지 못했습니다: 전문 모드는 워크스페이스가 필요합니다…`
  ★ 이때 `시작합니다` 안내는 남지 않는다.
- `@팀 실행 계획 어때?`처럼 "실행"이 명사구의 일부면 실행이 아니라 **팀
  상담**(⑤)으로 간다.

## ⑤ 역할 상담 / 팀 상담 / 상담 중 잠금

- `@검토자 이 구조에 리스크 있어?` → 검토 담당자 **한 명만** 답한다. 파일을
  고치지 않고, 응답에 전문 역할 배지가 붙지 않는다(일반 턴). Journal에
  `ROLE_STARTED`(`purpose: "consult"`)가 남고 `professionalRunId`는 null이다.
- ★ `@검토자 @기획자 …` → 검토자만 답하고
  `개별 역할 상담은 한 번에 한 명만 답합니다. 검토자만 응답하며 기획자은(는)
  이번에 제외됩니다…` 안내가 **응답이 시작된 뒤에** 남는다.
- 담당자를 지정하지 않은 역할 멘션 → `○○ 상담을 시작하지 못했습니다: …`
  안내만 남고 아무도 답하지 않는다.
- `@팀 이 설계 어때?` → `팀 상담 시작 · 기획자 → 검토자 → 구현자` 뒤에 세
  역할이 **순서대로 한 명씩** 답한다. 답하는 도중 **토론 시작**을 누르면
  `역할·팀 상담이 진행 중에는 토론을 시작할 수 없습니다`로 거부된다. 도중에
  `@검토자 …`를 또 보내도 거부 안내가 남는다.
- ★ 권한을 **대화만 (도구 없음)**으로 바꾼 뒤 `@구현자 왜 느려?` → 응답이
  파일을 읽었다고 주장하지 않는다("파일을 볼 수 없어 대화 기준으로" 정도가 정상).

## ⑥ 토론 — 자유토론 길이와 구조화 Preset

1. 주제를 하나 보낸 뒤 **토론 시작**.
2. 토론 방식 **자유토론**, 토론 길이 **짧게 (9턴)** 또는 **직접 설정**.

기대:
- 종료 메시지가 `토론 실행 예산(N회)에 도달해 여기서 마쳤습니다.`이거나
  결론(CONCLUDE) 요약이다. N이 고른 길이와 같다.
- ★ CLI 하나를 로그아웃한 채 같은 토론 → 나머지가 계속 말하고, 종료 문구에
  `(일부 응답 실패 포함)`이 붙는다. `모든 에이전트 응답이 실패해…`는 전원이
  실패했을 때만 나온다.
- 토론 방식 **구조화 토론**, Preset **기획 (발안자 → 비평가 → 발안자(수정) →
  종합자)**, 반복 1~2 사이클, 역할 슬롯 배정 후 시작 →
  `구조화 토론 시작 · 기획 Preset · … · N사이클(최대 M턴)`. 발언 순서가
  Preset과 정확히 같고, 중간 단계가 실패하면
  `<역할> 단계 응답 실패로 구조화 토론을 중단했습니다.`로 즉시 멈춘다.
- **Grill**, **Red Team**도 1사이클씩 돌려 순서를 확인한다.

## ⑦ 중지·개입·취소·복구

- 전체 실행 중 구현 단계에서 **중지** → 실행이 멈추고 Journal에
  `RUN_INTERRUPTED`. 다시 실행하면 이어서 진행된다.
- ★ Archivist(기록 정리) 응답이 오는 도중 **취소** →
  `기록 정리(Archivist)를 중지했습니다. 실행 완료 상태는 그대로 유지됩니다.`
  진행 표시가 완료로 남고 **실행 ▶**가 다시 열리지 않는다.
- 구현 도중 앱을 강제 종료하고 재시작 → 세션을 열면 중단 복구 안내가 보이고
  Journal에 `RUN_INTERRUPTED`가 있다. 그 뒤 PLAN을 다시 시작해도
  `HANDOFF_STALE` / `HANDOFF_DUPLICATE` 거부가 시스템 메시지로 반복 노출되지
  않는다(Journal에만 남는 것이 정상).
- 구현자가 `STATUS: BLOCKED`를 내면
  `아래에서 작업물을 유지하거나 복원하며 재기획으로 이어 주세요.` 안내와
  두 버튼(변경 유지 후 재기획 / 작업 전 복원 후 재기획)이 보인다.

## ⑧ 승인 대기 중 입력

- READY(승인 대기) 상태에서 일반 문장을 보내면 **기획 수정**으로 라우팅된다
  (버튼 라벨이 **기획 수정**). 기획자가 수정안을 내고 기획 검수가 다시 돈다.
- READY 상태에서 `@팀 실행 …`을 보내면 대기 중이던 실행을 버리고 새로
  시작한다(명시적 지시로 간주 — 의도된 동작). 확인 없이 교체되는 것이
  불편하면 보고한다.

## ⑨ 2차 리뷰 반영 변경점 ↔ 시나리오 대응표

| 변경점 | 확인 시나리오 |
| --- | --- |
| Archivist 전용 페르소나(그룹 채팅 참가자로 떨어지지 않음) | ② |
| 제어 줄 값의 인라인 백틱 보존(ASK_USER/COMPLETE/REASON) | ① |
| 제어 블록 뒤 꼬리 코드펜스 → 제어 미수용·펜스 보존 | ② |
| Handoff 예산을 자동 보완 횟수에 맞춰 확장 | ③ |
| 거부 사유가 행동에 영향(planner/recorder 대상)이면 사용자에게 표시 | ③ |
| 다중 역할 멘션 안내(시작 확인 뒤에만) | ⑤ |
| chat 권한 구현자 상담의 파일 읽기 오안내 제거 | ⑤ |
| 상담 중 토론·전문 실행·두 번째 상담 거부 | ⑤ |
| 자유토론 부분 실패 = 예산 도달 + 실패 포함 표기 / 전원 실패 = 실패 | ⑥ |
| '@팀 실행' 즉시 거부 시 '시작합니다' 미출력 | ④ |
| Archivist 진행 중 취소가 COMPLETED를 유지 | ⑦ |
| 완료 시 활성 invocation 정리(재실행 시 BUSY 거짓 거부 없음) | ②→③ 연속 실행 |
| 렌더러 '기록 정리' 단계 라벨·배지 | ② |

## 통과 기준

- ①~⑦이 기대대로 동작하고, 정상 흐름에서 `HANDOFF_REJECTED`가 사용자
  메시지로 노출되지 않는다.
- 어떤 역할 응답에도 제어 줄이 화면에 남지 않는다(모호한 제어 제외).
- Journal의 `type`이 모두 어휘 안이고(`professional-journal.js`의
  `JOURNAL_EVENT_TYPES`), `professionalRunId`가 같은 실행 안에서 일관된다.

## ⑩ 완료 전 사용자 확인(승인 대기)

검증 계획에 사람이 확인해야 하는 항목(HUMAN_APPROVAL)이 있는 작업을 **전체 실행 ⚡**
으로 돌린다. 예: 요구사항에 `발송 전 사람이 최종 확인`을 넣는다.

기대:
- 구현 검수까지 끝난 뒤 `승인이 필요한 항목이 남았습니다…` 시스템 메시지가 뜨고,
  입력창 위에 **확인할 항목 목록**이 나타난다. 항목 본문과 "사용자 확인이 필요한
  이유"가 함께 보인다.
- 입력창은 `아래에서 확인 항목을 승인하거나 거부해 주세요`로 바뀐다.
  (예전에는 `전문 실행이 끝난 뒤 입력할 수 있습니다`로 잠긴 채 풀 방법이 없었다.)
- **승인**을 누르면 그 항목이 사라지고, 남은 항목이 없으면 기록 단계로 이어져
  완료된다. 처리 중에는 두 버튼이 잠겨 중복 제출되지 않는다.
- **거부**하면 확인을 한 번 받은 뒤, 실행은 완료로 처리되지 않는다.
- 진행 표시는 이 동안 `구현검수`가 **대기 색**으로 남고(진행 중 색이 아니다),
  상태 줄은 `완료 전에 확인할 항목이 N건 있습니다.`로 나온다.

## ⑪ 진행 표시와 상태 문구

- **READY**: 상태 줄 `기획 검수를 통과했습니다. 실행을 기다리고 있습니다.` /
  진행 표시는 기획·기획검수가 완료색, **구현**이 대기색. **실행 ▶ 버튼이 눌린다.**
  (예전에는 이 상태에서 실행 버튼이 계속 비활성이었다.)
- **COMPLETED**: 다섯 단계 모두 완료색이고 진행 중인 단계가 없다. 상태 줄은
  `본 실행이 완료되었습니다.` 기록 정리(Archivist)를 중지했다면 그 사실만 덧붙고
  완료는 유지된다.
- **중단(INTERRUPTED)**: 진행 중과 다른 색으로 보이고, 다음 행동 안내가 붙는다.
- 상태 줄에 `Stop: USER_INTERRUPTED` 같은 내부 코드가 그대로 보이지 않는다.
  코드·Run id·백업 여부는 **자세히**를 펼쳤을 때만 나온다.

## ⑫ 막힘(BLOCKED) 복원 가능 여부

1. git 저장소가 **아닌** 워크스페이스에서 구현이 `STATUS: BLOCKED`로 멈추게 한다.

기대:
- 입력창 위 **다음 처리 선택** 버튼으로 막힘 처리 화면을 연다(헤더의 일반/전문
  토글은 이제 전환만 한다).
- `작업 전 복원 후 재기획`이 **비활성**이고, 이유가 툴팁으로 보인다.
  변경사항 처리 목록의 `작업 전으로 복원`·`작업 폐기`도 `— 복원할 백업 없음`으로
  잠겨 있다. `변경 유지` 계열은 그대로 쓸 수 있다.
- git 저장소에서는 같은 조작이 모두 활성이다.
- 처리에 실패하면 안내가 뜨고 **선택 화면이 다시 열린다**(닫힌 채 방치되지 않는다).
